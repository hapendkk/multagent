# 3. Выбор движка инференса

## 3.1. Требования к движку (из ТЗ)

1. Работа на **Windows-ноутбуке с 6 ГБ VRAM** (N2).
2. **Несколько моделей по очереди:** роутер, генератор и валидатор — модели разных семейств. В 6 ГБ они не помещаются одновременно, поэтому движок должен сам загружать и выгружать модели.
3. **Structured output** по JSON-схеме — на нём держится Jev-like модель решений.
4. **Tool calling.**
5. Квантованные модели (GGUF, Q4) — иначе модели на 4B не влезут.
6. HTTP API, желательно OpenAI-совместимый, чтобы движок можно было заменить без переписывания агентов.

## 3.2. Сравнение

Движков было шесть, и я честно перепробовала большинство — вот что из этого вышло:

| Движок | Плюсы | Минусы для нашего случая | Итог |
|---|---|---|---|
| **Ollama** | Нативно работает на Windows. Внутри llama.cpp (GGUF, Q4). Сам загружает и выгружает модели (`keep_alive`), так что три модели по очереди умещаются в 6 ГБ. `format` с JSON-схемой (structured output), tool calling, переключатель `think`. Собственный и OpenAI-совместимый API. Модели скачиваются одной командой `ollama pull` | Меньше тонких настроек, чем у чистого llama.cpp. Новые функции llama.cpp появляются с задержкой. Слабая пропускная способность при большом числе параллельных запросов. Контекст по умолчанию маленький, поэтому `num_ctx` задаём явно | **Выбран** |
| llama.cpp (`llama-server`) | Максимальный контроль: GBNF-грамматики, все параметры сэмплинга и квантизации. Немного быстрее Ollama. OpenAI-совместимый сервер | Один процесс — одна модель: для трёх моделей нужен ручной менеджмент или прокси (llama-swap). Модели надо скачивать и настраивать руками | Запасной вариант, если понадобится тонкий контроль |
| vLLM | PagedAttention и continuous batching: лучшая пропускная способность при многих пользователях. Стандарт для продакшн-серверов | Ориентирован на Linux + CUDA, на Windows только через WSL2. Заранее резервирует большую часть VRAM под одну модель, так что переключать три модели в 6 ГБ неудобно. Основной формат — FP16/AWQ/GPTQ, не GGUF | Для продакшн-сервера с мощной GPU, не для ноутбука |
| SGLang | Быстрый, RadixAttention (кеш общих префиксов), хорош для агентных цепочек | Те же ограничения, что у vLLM: Linux, серверные GPU | Не подходит под наше железо |
| LM Studio | Удобный GUI, внутри llama.cpp, OpenAI-совместимый сервер | Закрытое приложение, рассчитано на ручное использование. Автоматизация хуже, чем у Ollama | Удобен для ручных экспериментов |
| HF TGI | Продакшн-сервер от Hugging Face | Linux/Docker, тяжёлый для ноутбука | Не подходит |
| Облачные API (OpenAI, Anthropic и др.) | Сильнейшие модели, нет требований к железу | Брифы уходят наружу (нарушает N1), платно за каждый токен | Не требуется по ТЗ; возможен как «сильная» ветка роутинга |

## 3.3. Обоснование выбора

**Ollama** — единственный вариант, который закрывает все требования «из коробки» на нашем железе:
- автоматическое переключение трёх моделей разных семейств в 6 ГБ VRAM;
- structured output по схеме для Jev-like модели;
- tool calling;
- нативная работа на Windows.

Ollama использует llama.cpp внутри. Поэтому по скорости на одного пользователя мы почти ничего не теряем: все модели в замерах работали на GPU на 100% (кроме qwen3 8B, которая не помещается в VRAM).

## 3.4. Риски и как их закрываем

| Риск | Мера |
|---|---|
| Привязка к Ollama | `llm.py` — тонкая обёртка над HTTP. Переход на llama.cpp server или vLLM через OpenAI-совместимый API меняет только этот файл |
| Маленький контекст по умолчанию обрезает промпт | `num_ctx` задаётся явно: 4096 для UX, 12288 для генерации |
| Thinking-модели тратят лимит токенов на размышления | `think=False` по умолчанию, с автоматическим откатом для моделей, которые этот параметр не принимают |
| Модели долго загружаются при переключении | `keep_alive="10m"`. Дальше: держать маленький роутер (2 ГБ) в памяти постоянно |
| Низкая пропускная способность при многих пользователях | Для многопользовательского режима — vLLM на сервере с GPU 24 ГБ и больше |
