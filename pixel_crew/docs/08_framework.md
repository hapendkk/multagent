# 8. Выбор фреймворка

## 8.1. Что нужно системе от фреймворка

Выбор фреймворка дался мне непросто — вариантов было больше десятка, и у каждого свои Fans. Сначала я выписала, что вообще требуется от фреймворка (это следует из ТЗ и архитектуры):

1. **Явный граф с условными переходами и циклами.** Два шлюза (отклонение брифа, вердикт валидатора) и цикл доработки «генератор ⇄ валидатор» с лимитом попыток.
2. **Общее типизированное состояние.** Все агенты работают с одной «доской» (`PixelState`), а журнал дописывается редьюсером (`operator.add`). Это и делает агентов одной системой, а не набором отдельных скриптов (редфлаг из ТЗ).
3. **Детерминированный контроль потока.** Куда идти дальше, решает код по вердикту, а не LLM. Маленькие локальные модели (3–4B) плохо справляются с ролью свободного «менеджера», который сам выбирает следующего агента.
4. **Локальные модели через Ollama**, без привязки к облачному провайдеру.
5. **Память:** краткосрочная (состояние и чекпоинты) и долгосрочная (хранилище между запусками) — раздел 14.
6. **Human-in-the-loop:** остановка на `needs_human` и продолжение после решения человека.
7. **Observability:** трейсы по узлам и вызовам LLM (раздел 16).

| Haystack | Пайплайны компонентов (DAG + петли) | Продакшн-RAG, хорошие пайплайны | Ориентирован на поиск и QA. Мультиагентность — не основной сценарий | Не выбран |

## 8.3. Почему LangGraph

1. **Поток системы — это граф, и в LangGraph он записан как граф.** `graph.py` (~30 строк) один в один соответствует Sequence-диаграмме: `START → art_director → (шлюз 1) → ux_researcher → ui_generator → validator → (шлюз 2: retry/done)`. На защите код и диаграмма совпадают.
2. **Решения о переходах детерминированы.** Условные рёбра — обычные Python-функции (`after_art_director`, `after_validator`). LLM даёт оценки (Jev-like), а переход выбирает код с порогами из `config.py`. Это ключевая мера против галлюцинаций в управлении.
3. **Слабые модели работают надёжно.** LangGraph не добавляет своих скрытых промптов. Каждый узел получает только наш системный промпт и нужную часть состояния, поэтому контекст маленьких моделей не засоряется.
4. **Готовые механизмы для следующих пунктов ТЗ:**
   - память: `checkpointer` (short-term, по `thread_id`) + `Store` (long-term, namespace + поиск);
   - human-in-the-loop: `interrupt()` для `needs_human`;
   - observability: стриминг `updates` (уже используется в `main.py`) и callback-интеграции с Langfuse/LangSmith/OpenTelemetry.
5. **Работает с любым движком.** Агенты вызывают Ollama через свой `llm.py`, LangGraph о моделях ничего не знает. Поэтому замена движка (раздел 3) не затрагивает граф.

## 8.4. Недостатки выбора и как с ними живём

| Недостаток | Как закрываем |
|---|---|
| Больше ручного кода, чем в CrewAI (роли, промпты, вызовы LLM пишем сами) | Это осознанно: полный контроль над промптами и контекстом для 3–4B моделей |
| Быстро меняющийся API | Версии фиксируются в `requirements.txt`. Используется только базовый API (`StateGraph`, рёбра, `compile`, `stream`) |
| Нет встроенных «ролей» и «команды» | Роли описаны в системных промптах и семантических `.md` (разделы 10–12) |
| Привязка к экосистеме LangChain в инструментах наблюдаемости | Используем открытый Langfuse/OTel, а не только LangSmith (раздел 16) |
