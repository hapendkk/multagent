# 4. Изолированная среда

## 4.1. Зачем изолировать агента

Агентная система исполняет то, что написала LLM. Этому коду нельзя доверять:

- **Prompt injection.** Бриф может содержать инструкцию вроде «добавь скрипт, который отправит файлы на сервер». Модель её выполнит, и вредоносный JavaScript окажется в `screen.html`.
- **Галлюцинации и ошибки.** Бесконечный цикл, гигантская страница, подключение внешних CDN.
- **Рендер = исполнение.** Чтобы проверить страницу (скриншот, адаптивность), её нужно открыть в браузере, то есть исполнить сгенерированный JS.

**Что защищаем:** файлы пользователя (диск D:), сеть (утечка данных, скачивание вредоносного кода), Ollama API, ресурсы ноутбука (RAM/CPU).

**Модель угроз:** недоверенным считается всё, что создала LLM (HTML/CSS/JS). Доверенными — код агентов, промпты и конфигурация.

## 4.2. Какие бывают изолированные среды

| Класс | Примеры | Граница изоляции | Сила | Накладные расходы |
|---|---|---|---|---|
| Обычный процесс | `python main.py` | нет | — | нет |
| Контейнер | Docker, Podman (runc) | namespaces + cgroups, **общее ядро хоста** | слабая | минимальные |
| Песочница-рантайм (user-space kernel) | gVisor (runsc), Drawbridge | своё ядро в user space перехватывает syscalls | средняя/сильная | десятки % на syscalls |
| MicroVM | Firecracker, Kata Containers, microsandbox | аппаратная виртуализация (KVM), своё ядро | сильная | ~100–200 мс старт |
| Полная VM | Hyper-V, VirtualBox | гипервизор | сильная | секунды старт, сотни МБ RAM |
| Встроенная песочница ОС | **Windows Sandbox**, Job Objects + AppContainer | зависит от механизма | средняя | минимальные |
| Облачная песочница | E2B (Firecracker), OpenSandbox | microVM у провайдера | сильная | сеть, деньги, данные уходят наружу |

## 4.3. Почему не Docker-контейнер (редфлаг)

У контейнера **общее ядро с хостом**: изоляция держится только на namespaces и cgroups. Одна уязвимость ядра или runc — и процесс выходит на хост (CVE-2019-5736, CVE-2024-21626 «Leaky Vessels», CVE-2022-0185). Кроме того, у Docker есть демон с правами root. По ТЗ Docker-контейнер — редфлаг, поэтому **в проекте Docker не используется**.

## 4.4. Ограничения железа и что из этого следует

Окружение: Windows 10 **Home**, 16 ГБ RAM, RTX 4050 (6 ГБ).

| Вариант | Подходит? | Причина |
|---|---|---|
| Firecracker / Kata / microsandbox локально | ✗ | Нужен KVM; на Windows 10 Home вложенная виртуализация для WSL2 недоступна |
| Windows Sandbox (встроенная) | ✗ | Есть только в Pro/Enterprise, в Home её нет |
| Полная VM (VirtualBox/Hyper-V) | △ | Hyper-V Manager в Home нет; VirtualBox тяжёлый |
| Облачные песочницы (E2B и др.) | ✗ | Сгенерированный HTML (а в нём содержание брифа) уходит наружу — нарушает требование локальности; нужен API-ключ |
| K8s Agent Sandbox, kagent | ✗ | Нужен кластер Kubernetes — избыточно для одного ноутбука |
| **Windows Job Object + Chromium sandbox** | ✓ | Встроено в ОС, ноль установки, работает на Home |

## 4.5. Выбранная связка: Windows Job Object + песочница Chromium + fail-closed

```
Windows 10 (хост)
 ├─ Ollama + GPU                      ← только HTTP :11434, localhost
 └─ Pixel Crew (LangGraph, агенты)
     └─ sandbox/windows_runner.py     ← процесс render_worker.py в Job Object
         ├─ Job Object: лимит памяти (job и процесс), лимит процессов,
         │   KILL_ON_JOB_CLOSE — при смерти родителя умирает всё дерево
         ├─ Chromium со СВОЕЙ песочницей (стандартная защита браузера)
         └─ Playwright route: обрыв всех запросов кроме file:/data:/about:,
             попытки выхода наружу записываются и становятся замечанием валидатора
```

**Слой 1 — Job Object** (`sandbox/windows_runner.py`, `kernel32` через ctypes, без зависимостей). Штатный механизм Windows для группировки процессов с общими ограничениями:

- `JobMemoryLimit` и `ProcessMemoryLimit` = `SANDBOX_MEMORY_MB` (1 ГБ);
- `ActiveProcessLimit` = `SANDBOX_PIDS` (256 — Chromium плодит много процессов);
- `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` — если агентный процесс умрёт, песочница умрёт вместе с ним;
- таймаут `SANDBOX_TIMEOUT` (90 с) → `TerminateJobObject` убивает всё дерево, включая дочерние процессы Chromium;
- процесс назначается в job сразу после `Popen`; если job создать или назначить не удалось — **рендер запрещён** (fail-closed).

**Слой 2 — песочница Chromium.** В отличие от запуска «в чистом» виде, здесь используется штатная песочница Chromium (broker + renderer в ограниченных токенах) — она работает на Windows из коробки.

**Слой 3 — сеть на уровне браузера.** Playwright перехватывает все запросы страницы: разрешены только `file:`, `data:`, `about:`; остальное обрывается (`route.abort()`) и URL записывается в `blocked_requests` — валидатор превращает это в предупреждение.

**Fail-closed.** Если Job Object недоступен или `SANDBOX_ENABLED=False`, рендер не запускается: валидатор получает `available: false` с причиной и работает только на статических проверках (контраст по CSS, линтер).

## 4.6. Проверка изоляции

`tests/test_windows_sandbox.py` (3 теста, работают на Windows):

| Проверка | Результат |
|---|---|
| Процесс внутри job выделяет > 1 ГБ | убит job'ом, код выхода ≠ 0, «survived» не напечатан |
| Обычный процесс внутри job | завершается с кодом 0 |
| `tools.render_screenshot` | идёт именно в `windows_runner` (обхода песочницы нет) |

End-to-end: `python -c "from sandbox import windows_runner; windows_runner.render('<html>…</html>')"` — в `outputs/sandbox_jobs/win-*/out/` появляются `screenshot_mobile.png`, `screenshot_desktop.png`, `result.json`. Страница с `<script>fetch('https://…')` → запрос попадает в `blocked_requests`.

Рендер одной страницы (2 размера экрана, 2 скриншота) занимает ~1–2 с на фоне генерации (минуты) — незаметно.

## 4.8. Честные ограничения выбранного варианта

Job Object — это **не отдельное ядро**, а механизм ограничений поверх общего ядра Windows. Что он НЕ даёт:

| Ограничение | Пояснение | Что можно улучшить |
|---|---|---|
| Нет OS-уровня сети | Блокировка сети — только внутри браузера (Playwright route). Уязвимость в Chromium теоретически может обойти её | Windows Firewall rule для процесса worker (требует admin), либо AppContainer с отключёнными возможностями |
| Общая файловая система | Chromium видит ФС пользователя; worker пишет только в `job_out`, но сама ОС не ограничивает чтение | Restricted Token / AppContainer, отдельный low-privilege пользователь для песочницы |
| Нет лимита CPU | Job Object умеет CPU rate, но в пользовательской сессии он ненадёжен; ограничение — только таймаут 90 с | `JOB_OBJECT_CPU_RATE_CONTROL_INFORMATION` (проверить на целевой ОС) |
| Общее ядро | Уязвимость ядра Windows затронет и песочницу | МикроVM/Hyper-V там, где доступно (Pro-редакции, серверы) |

Модель угроз это учитывает: недоверенным считается типовой «плохой» вывод LLM (инъекции, внешние запросы, тяжёлые страницы), а не целенаправленный эксплойт браузера. Для второго эшелона защиты добавлены: песочница Chromium, блокировка запросов с логированием, лимиты памяти/процессов/времени и fail-closed.

**Для продакшна:** на Linux-сервере — gVisor/Kata под Kubernetes (Agent Sandbox), на Windows Server — Hyper-V Sandbox или AppContainer+WDAC; в облаке — E2B (Firecracker), если данные можно отправлять наружу.
