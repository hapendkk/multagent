# 14. Память агента

## 14.1. Слои

| Слой | Что хранит | Где | Срок жизни | Кто пишет / читает |
|---|---|---|---|---|
| **L1 рабочая (short-term)** | `PixelState`: бриф, задание, HTML, вердикт, замечания, журнал; чекпоинт после каждого узла | LangGraph `InMemorySaver`, `thread_id = run_…` | один запуск | все агенты через граф |
| **L2 эпизодическая (long-term)** | Каждый запуск: бриф, тип, сложность, модель, исход, попытки, качество, категории проблем, название | SQLite `memory/pixel_memory.db`, таблица `runs` | 90 дней, не больше 500 записей | пишет `main.py` после запуска; UX Researcher получает 2 похожих прошлых брифа |
| **L3 семантическая / процедурная (уроки)** | Повторяющиеся проблемы по типу экрана → готовое правило («hover темнее базы») | таблица `lessons` | затухание, удаление через 60 дней без повторов | пишет `record_run`; UI Generator получает до 3 уроков |
| Кэш | Решение Jev-like роутера для того же брифа | таблица `cache` | 7 дней | Art Director |

L1 — это то, что модель держит «в голове» сейчас. L2 — что было раньше. L3 — чему студия научилась. Кэш экономит 3 голоса роутера (~10–20 с) на повторном брифе.

## 14.2. Почему такая реализация

Тут я тоже долго сомневалась — Mem0, Zep, LangGraph Store, везде что-то модное. В итоге остановилась на SQLite + stdlib, и вот почему:

- **SQLite + stdlib.** Локально (требование N1), без сервера и Docker, один файл. Объёмы малы: сотни запусков.
- **Без векторной БД.** Похожие брифы ищутся по пересечению слов (Jaccard) с бонусом за тот же тип экрана. На сотнях коротких брифов этого достаточно. Эмбеддинги через Ollama (`nomic-embed-text`) — путь развития. Альтернативы (Mem0, Zep/Graphiti, LangGraph Store + pgvector) избыточны для одного ноутбука.
- **Детерминированная запись.** Уроки выводятся из замечаний *инструментов* по словарю категорий (`memory.CATEGORIES`). Текст урока написан заранее, а не сгенерирован LLM. Поэтому:
  - галлюцинация модели не может «записаться» в память;
  - prompt injection из брифа не попадёт в будущие промпты: бриф в L2 хранится, но в промпт идёт только как цитата похожего задания, не как правило.
- **Отклонённые брифы не сохраняются** (`outcome = rejected`): не-UI запросы не засоряют память.

### 14.2.1. Рассмотренные альтернативы

ТЗ требует сравнить готовые фреймворки памяти. Что есть на рынке и почему не подошло:

| Инструмент | Что это | Почему не выбран |
|---|---|---|
| **Mem0** | Универсальный слой памяти (user/session/agent), облако или self-host | Self-host тянет векторную БД и LLM-экстрактор фактов — а у нас запись *детерминированная*, LLM в память не пишет вовсе. Облако нарушает локальность |
| **Zep / Graphiti** | Темпоральный граф знаний, гибридный retrieval, инкрементальные обновления | Ориентирован на диалоги и сущности пользователя. У нас нет корпуса текстов для графа: память — это счётчики проблем по типам экранов. Граф из ~9 категорий — оверкилл |
| **Letta (ex-MemGPT)** | Агенты с редактируемой памятью (block memory), собственная платформа | Память редактирует сама LLM — прямой риск отравления и галлюцинаций. Нужен их сервер/SDK, а не наш граф |
| **LangMem** | Примитивы памяти от LangChain (извлечение фактов из диалогов, оптимизация промптов) | Привязан к LangChain-экосистеме; извлечение — снова LLM-запись. У нас LangGraph без LangChain-обёрток |
| **memU** | Память как файловая система для проактивных агентов 24/7 | Проактивность и файловая иерархия не нужны batch-системе генерации экранов |
| **LlamaIndex / RAGFlow / PageIndex** | RAG-движки: ingestion, индексы, retrieval по документам | См. ниже — RAG здесь не оптимален в принципе |
| **Cognee** | Движок «динамической памяти»: векторный + графовый поиск | Та же история: нужен корпус документов и embeddings-пайплайн; наших данных (счётчики категорий) для этого мало |
| **SuperMemory / Rowboat** | Персональные базы знаний из почты/заметок, граф знаний | Чужой домен (личные данные пользователя), не про уроки дизайн-студии |
| **LangGraph Store + pgvector** | Встроенное хранилище LangGraph с векторным поиском | Требует Postgres+pgvector — сервер и Docker там, где у нас один ноутбук и stdlib |

### 14.2.2. Почему RAG — не оптимальный вариант именно здесь

Самое сложное было объяснить себе, почему я не взяла векторную БД. Все вокруг говорят «RAG — это память», но у меня задача другая. RAG (и всё, что на нём построено: векторные БД, графы знаний, эмбеддинги) отвечает на вопрос «найди похожий *текст*». Наша память отвечает на другие вопросы:

1. **«Какие ошибки повторяются на этом типе экрана?»** — это агрегация по *категориям*, а не поиск по тексту. Ответ вычисляется счётчиком `count`/`resolved`, а не косинусным расстоянием между брифами.
2. **«Насколько урок ещё актуален?»** — это затухание по времени и статистика исправлений, которых нет ни в одном RAG-фреймворке «из коробки»: их retrieval не различает «урок, который чинили 10 раз» и «урок, который чинили 1 раз».
3. **Нет корпуса.** RAG окупается на тысячах документов. У нас — сотни коротких брифов и 9 фиксированных категорий проблем. Jaccard по словам брифа (`similar_runs`) даёт тот же эффект за 0 зависимостей.
4. **Детерминизм.** В RAG-фреймворках память пишет LLM (экстракция фактов, summarization) — а это канал для галлюцинаций и prompt injection. У нас уроки выводятся из замечаний *инструментов* по словарю: записать в память может только валидатор, и только в виде заранее написанного правила.

Когда RAG/эмбеддинги всё же имеют смысл: если брифы станут длинными документами (ТЗ на продукт, дизайн-система) или если похожих брифов станут тысячи — тогда `nomic-embed-text` через Ollama + таблица эмбеддингов в той же SQLite. Это путь развития, а не текущее состояние.

## 14.3. Правила актуализации

1. **Подкрепление.** Каждое повторение проблемы на этом типе экрана: `count + 1`, `last_seen = сейчас`.
2. **Затухание.** Вес урока:
   \[ score = count \cdot 0.5^{\,\Delta t / 14\,\text{дней}} \cdot \left(1 - 0.5 \cdot \frac{resolved}{count}\right) \]
   Урок, который давно не повторялся, слабеет. Урок, который генератор всегда легко исправлял на доработке (`resolved`), весит меньше.
3. **Порог.** В промпт идут только уроки с `score ≥ 0.5`, не больше 3 штук.
4. **Забывание** (`prune()` после каждого запуска):
   - уроки без повторов > 60 дней и со слабым весом удаляются;
   - эпизоды старше 90 дней или сверх 500 удаляются;
   - кэш старше 7 дней удаляется.
5. **Кэш только для уверенных решений.** Решение роутера кэшируется, если уверенность по всем трём вопросам ≥ 0.7.
6. **Отключение.** `PIXEL_MEMORY=0` — запуск «с чистого листа», например для честных Evals без утечки между прогонами.

## 14.4. Как память влияет на поток

```
Art Director ──► cache_get(brief) ──► есть: решение без 3 голосов │ нет: голосование → cache_put
UX Researcher ──► similar_runs(brief) ──► «похожие задания: итог fail, проблемы: contrast»
UI Generator ──► get_lessons(type) ──► «Уроки студии: hover темнее базы…»
main.py (конец) ──► record_run(state, замечания по попыткам) ──► runs + lessons + prune
```

Что попало в память, видно в `report.json` (поле `memory`) и в журнале (`уроки из памяти: …`, `из кэша памяти`).

## 14.5. Проверка

`tests/test_memory.py` (7 тестов):
- категоризация замечаний;
- накопление уроков и выдача по типу экрана;
- затухание и удаление по TTL;
- поиск похожих запусков, отклонённые не сохраняются;
- TTL кэша и нормализация брифа;
- отключение памяти.

Тесты используют временную БД (`tests/conftest.py`). Всего в проекте 45 тестов.
