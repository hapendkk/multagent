# 15. Evals системы

Бенчмарк моделей (раздел 1) оценивает отдельные LLM — это была моя «проверка перед покупкой». А Evals оценивают **всю систему**: граф, роутинг, инструменты, песочницу и шлюзы. Каждый бриф проходит через систему целиком, как реальный пользователь.

## 15.1. Набор данных (`evals/briefs.jsonl`, 12 брифов)

| Группа | Брифы | Что проверяют |
|---|---|---|
| Типичные UI | B01–B08: форма входа, лендинги (рус/англ), дашборды, мобильные экраны, форма записи | качество, роутинг типа и сложности |
| Размытый | B09 «сделай что-нибудь красивое» | поведение при неясном брифе |
| Негативные | N01 рецепт, N02 интеграл | шлюз 1: не-UI отклоняются |
| Безопасность | S01 prompt injection с внешним `<script>` | инъекция не попадает в HTML, песочница блокирует сеть |

Для каждого брифа размечены эталоны: `is_ui`, `type` и допустимый диапазон `complexity`.

## 15.2. Метрики

**Продуктовые** (что получает пользователь)

| Метрика | Смысл | Порог |
|---|---|---|
| `pass_rate` | доля UI-брифов с PASS | ≥ 0.6 |
| `first_try_pass_rate` | PASS с первой попытки | — |
| `avg_attempts`, `needs_human_rate` | стоимость доработок, доля эскалаций человеку | — |
| `rejection_accuracy` / `false_rejection_rate` | не-UI отклонены / UI ошибочно отклонены | 1.0 / — |
| `contrast_clean_rate` | итоговые страницы без провалов контраста | ≥ 0.9 |
| `mobile_overflow_rate` | горизонтальный скролл на 375 px (рендер в песочнице) | — |
| `injection_blocked_rate` | инъекция не попала в HTML | 1.0 |

**LLM** (как работают модели)

| Метрика | Смысл | Порог |
|---|---|---|
| `router_is_ui_accuracy`, `router_type_accuracy`, `complexity_band_accuracy` | точность Jev-like роутера против разметки | тип ≥ 0.7 |
| `router_confidence_mean` | средняя уверенность голосования | — |
| `validator_tool_agreement` | вердикт валидатора совпадает с объективными инструментами | — |
| `judge_mean` | **LLM-as-a-Judge**: третья модель другого семейства, чем генератор и валидатор; 3 голоса × 3 критерия (соответствие брифу, визуальная иерархия, удобство), шкала 0–100 | ≥ 60 |
| `tool_calls_per_run` | сколько раз агент сам вызвал инструменты | — |
| `escalation_rate`, `light_model_share` | работа роутинга: доля лёгкой модели и эскалаций | — |

**Инфраструктурные**

| Метрика | Смысл | Порог |
|---|---|---|
| `latency_p50_s`, `latency_p95_s` | время запуска целиком | p95 ≤ 420 с |
| `node_seconds_mean` | среднее время каждого агента: где узкое место | — |
| `error_rate` | падения из-за Ollama и таймаутов | 0 |
| `sandbox_available_rate` | рендер в песочнице (Job Object) действительно работал | 1.0 на Windows; иначе «нет данных» |

## 15.3. Методика

- Перед прогоном задаётся `PIXEL_MEMORY=0`, чтобы уроки из прошлых брифов не завышали результат. Эффект памяти измеряется отдельно: второй прогон с `PIXEL_MEMORY=1`, затем сравнение `pass_rate` и `avg_attempts`.
- Судья не совпадает по семейству ни с генератором, ни с валидатором (`config.JUDGE_CANDIDATES`). Это снижает self-preference bias.
- Пороги работают как регрессионный шлюз: код выхода 1 при нарушении. Правки промптов, skills и моделей принимаются только без регресса.
- Отчёт: `evals/results/<время>/summary.md` (таблицы метрик и брифов) и `results.json` (сырые данные и траектории).

## 15.4. Запуск

```bat
set PIXEL_MEMORY=0
python evals\run_evals.py               :: все 12 брифов, около 40–60 мин на RTX 4050
python evals\run_evals.py --ids B01,N01 --no-judge   :: быстрая проверка
```

Расчёт метрик и порогов покрыт `tests/test_evals.py`. Всего в проекте 45 тестов. Реальный прогон нужно сделать на ноутбуке с Ollama и вставить `summary.md` в отчёт.

## 15.5. Непрерывный мониторинг

Evals — это офлайн-гейт перед приёмкой изменений, а «мониторинг перформанса» — это накопление тех же метрик на каждом реальном запуске. У нас это одна система, а не две:

- **Каждый запуск `main.py` пишет `metrics.jsonl`** (`obs.finish()`): исход, попытки, время, токены, ошибки LLM, доступность песочницы — те же поля, что и в evals-отчёте.
- **Алерты считаются на каждом финише** (`check_alerts`): `slow_run`, `llm_errors`, `sandbox_down`, `slow_model`, `needs_human`, `run_failed`, `pass_rate_drop` (скользящий pass rate за последние 10 запусков). Пишутся в `alerts.jsonl` и печатаются в консоль.
- **Сводка по требованию:** `python observability.py` — исходы, p50/p95 времени, токены, ток/с по моделям, последние алерты. Формат JSONL совместим с OTel — при переезде на Phoenix/Langfuse мониторинг не изменится.

Для «непрерывности» без сервера достаточно планировщика ОС: например, Task Scheduler → `python evals/run_evals.py --no-judge` раз в сутки/неделю — код выхода 1 при регрессе можно завязать на уведомление. Метрики и алерты от обычных пользовательских запусков копятся в `outputs/telemetry/` независимо от расписания.
