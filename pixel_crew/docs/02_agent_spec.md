# 2. Техническое задание на мультиагентную систему Pixel Crew

Это ТЗ я писала сама под свой проект — формулировки функциональных требований (F1–F17) потом один в один закрываются кодом и тестами.

## 2.1. Назначение

Pixel Crew — автономная мультиагентная «дизайн-студия» на базе локальных LLM.
По текстовому брифу на естественном языке она выдаёт готовый экран интерфейса: самодостаточный HTML-файл, который проверен на соответствие брифу, доступность (WCAG AA) и базовое качество вёрстки.

**Проблема.** Одна LLM, которую просят «сделать экран», выдаёт код без проверки: низкий контраст, нет адаптивности, забытые элементы брифа. Человеку приходится проверять и переделывать вручную.

**Решение.** Разделить работу между специализированными агентами: постановка задачи, UX, вёрстка и независимая проверка. Проверку делает модель другого семейства вместе с детерминированными инструментами, а при провале запускается цикл доработки.

## 2.2. Пользователи и сценарии

| Пользователь | Сценарий |
|---|---|
| Продуктовый менеджер / основатель | Быстро получить кликабельный прототип экрана по описанию идеи |
| Дизайнер | Получить черновик экрана с соблюдённой доступностью как стартовую точку |
| Разработчик | Получить чистый HTML/CSS на дизайн-токенах для дальнейшей вёрстки |

Основной сценарий:
1. Пользователь запускает `python main.py "бриф"`.
2. Система показывает ход работы агентов в консоли.
3. В `outputs/run_<время>/` сохраняются `screen.html` и `report.json`.
4. Пользователь открывает экран в браузере.

## 2.3. Входные и выходные данные

**Вход:** бриф на русском или английском (1–5 предложений). Пример: «Мобильное приложение для медитации: экран выбора длительности сессии. Аудитория 25–35 лет. Спокойный тон.»

**Выход:**
- `screen.html` — один файл, CSS внутри, без внешних ресурсов.
- `report.json` — бриф, задание, решения роутера с уверенностью, вердикты валидатора, журнал шагов, время.
- Итог работы — один из пяти:
  - `pass` — проверка пройдена;
  - `fail` — не прошла за N попыток, сохранена последняя версия;
  - `needs_human` — валидатор не уверен;
  - `rejected` — бриф не про интерфейс;
  - `running` — промежуточное состояние.

## 2.4. Функциональные требования

### Агенты

| ID | Агент | Требование |
|---|---|---|
| F1 | Art Director (оркестратор) | Классифицировать бриф Jev-like моделью решений: UI-запрос (да/нет), тип продукта (из списка), сложность (0–100), у каждого ответа своя уверенность |
| F2 | Art Director | Отклонять бриф, если это не UI-запрос с уверенностью ≥ `CONF_THRESHOLD` (входной шлюз) |
| F3 | Art Director | Маршрутизировать задачу на модель по сложности: лёгкая или сильная (роутинг для экономии ресурсов) |
| F4 | Art Director | Составить структурированное задание: название, аудитория, тон, главный экран, ключевые элементы (JSON по схеме) |
| F5 | UX Researcher | Подготовить персону, сценарий, структуру экрана и риски доступности (до 250 слов) |
| F6 | UI Generator | Сгенерировать HTML по жёстким требованиям: семантика, токены в CSS-переменных, mobile-first, контраст ≥ 4.5:1, `:focus-visible` |
| F7 | UI Generator | При доработке исправлять только замечания валидатора и возвращать полный файл |
| F8 | Validator | Запускать детерминированные инструменты: расчёт контраста WCAG, линтер HTML, рендер страницы |
| F9 | Validator | Оценивать «соответствует брифу» и «качество 0–100» Jev-like голосованием на модели **другого семейства**, чем генератор |
| F10 | Validator | Выносить вердикт `pass` / `fail` / `needs_human` и формировать конкретные замечания с точными исправлениями цветов |

### Система

| ID | Требование |
|---|---|
| F11 | Цикл доработки: не более `MAX_ATTEMPTS` (3) попыток генерации |
| F12 | Общее состояние (shared state) для всех агентов, журнал шагов дописывается и не перезаписывается |
| F13 | Краткосрочная память: состояние текущего запуска и история попыток. Долгосрочная память: удачные решения и типичные ошибки прошлых запусков, предпочтения пользователя |
| F14 | Скиллы агентов в виде отдельных файлов, подгружаются по задаче |
| F15 | Семантические .md-файлы идентичности студии (ценности, стиль, принципы, как SOUL.md) |
| F16 | Трассировка каждого шага и вызова LLM (Observability): время, токены, модель, вердикты |
| F17 | Набор Evals: эталонные брифы и автоматический прогон с метриками качества |

## 2.5. Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| N1 | Локальность / приватность | Все LLM работают локально (Ollama), брифы не уходят во внешние API |
| N2 | Железо | Работа на ноутбуке с GPU 6 ГБ VRAM: каждая модель ≤ ~4.6 ГБ в Q4_K_M, модели подгружаются по очереди |
| N3 | Время | Один бриф с учётом доработок — не более 6 минут. Целевое время — ≤ 3 минуты |
| N4 | Надёжность | Нечитаемый ответ модели не роняет систему: запасные режимы `schema → json → plain`, значения по умолчанию, понятные сообщения об ошибках |
| N5 | Изоляция | Сгенерированный HTML рендерится и проверяется только в изолированной песочнице: без сети, с ограниченной файловой системой и лимитами CPU/RAM/времени |
| N6 | Безопасность | Ввод пользователя не исполняется как код. Агенты не имеют доступа к файловой системе за пределами `outputs/` |
| N7 | Воспроизводимость | Все пороги и модели заданы в `config.py`, каждый запуск полностью описан в `report.json` |
| N8 | Борьба с галлюцинациями | Всё, что можно посчитать (контраст, структура), считает код. LLM получает готовые цифры. Валидатор — модель другого семейства. Низкая уверенность передаёт решение человеку |
| N9 | Расширяемость | Новый агент добавляется как узел графа LangGraph без изменения остальных |

## 2.6. Шлюзы качества и пороги

| Шлюз | Условие | Действие |
|---|---|---|
| Входной | `is_ui_request = false` и уверенность ≥ 0.7 | `rejected`, стоп |
| Жёсткие проверки | Есть провалы контраста или ошибки линтера | `fail`, доработка с точными замечаниями |
| Уверенность валидатора | Уверенность в «соответствует брифу» < 0.7 | `needs_human` |
| Оценка качества | `matches_brief = true` и `quality ≥ 60` | `pass` |
| Лимит попыток | `attempt = 3` | Сохранить последнюю версию с замечаниями |

## 2.7. Ограничения и что не входит в объём

- Один бриф — один экран. Многостраничные сайты и навигацию между экранами система не делает.
- Нет растровой графики: только CSS и inline SVG.
- Нет реальной бизнес-логики и бэкенда, только статическая вёрстка.
- Проверка контраста статическая: градиенты, прозрачность и картинки под текстом не учитываются до появления рендера в песочнице.

## 2.8. Критерии приёмки

1. По брифу из эталонного набора система за ≤ 6 минут выдаёт `screen.html` и `report.json`.
2. Доля `pass` на эталонном наборе ≥ 60%.
3. В выдачах с `pass` нет провалов контраста по надёжным парам и ошибок линтера.
4. Брифы не про интерфейсы (например, «напиши стихотворение») отклоняются.
5. Генератор и валидатор работают на моделях разных семейств. Это проверяется по `report.json`.
6. Каждый запуск виден в системе наблюдаемости как трейс со спанами агентов и вызовов LLM.
